# Changelog

All notable changes to OpenBrain are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and version numbers follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## 0.1.0-alpha.3 - 2026-08-14

Nothing added below is armed by default. A vault created with `init` still ships with all seven capabilities disarmed; every item below is something you can turn on, not something that started running.

### Added

- Seven optional capabilities (`hooks`, `capture`, `transcripts`, `classifier`, `learning`, `learning.evaluate`, `learning.consolidate`), inspected and armed one at a time with `open-brain capabilities list|explain|enable|disable`, or walked through together with `open-brain onboarding`.
- `open-brain hooks install|uninstall|status` and `open-brain hook <event>`: a single, idempotent entry point that wires OpenBrain into Claude Code and Codex hook events (session start, prompt submit, pre/post tool use, stop, pre-compact), with a documented JSON contract, a 2000ms per-hook time budget, and a manual fallback command for any CLI with no hook mechanism.
- `open-brain guard`: the pre-effect check a `PreToolUse` hook uses to refuse direct writes to the preference ledger and its generated core.
- A second, post-effect layer of tamper evidence for the preference kernel, independent of hooks: every legitimate write is recorded with its provenance, and any content that does not match the last recorded write is detected, not prevented.
- `open-brain capture scan|mine|markers`: deterministic, local extraction of preference and memory candidates from a transcript or from whatever a hook already saw, behind a documented marker pre-filter.
- `open-brain transcripts scan|show|purge`: reads session transcripts only from directories named through `capabilities enable transcripts --path`, consent per path and never global, with redaction on by default and a documented list of what it covers and what it does not.
- `open-brain classify [--dry-run]`: sends staged candidates to a model for typing and scoring, capped by a daily call budget, and prices a run before it can ever spend one. The only capability that spends money or sends anything off the machine.
- `open-brain staging list|show|add|drop|compact|status` and `open-brain sync pending|staged|prepare|show|resume|validate|apply|undo`: the human gate between anything staged and the preference kernel. `sync validate` (alias `sync apply`) is the only path from that gate into the kernel; `prefs add` is a second, deliberate door, for a preference you state yourself, and both demand the same proof that a human is present. `sync undo` reverses an applied batch from a record written before the batch and sealed after it, not from git; it works on a vault that is not a git repository at all.
- `open-brain learn status|mirror|journal|sensors|evaluate|beliefs|rollback|consolidate`: a decision journal, sensors, an evaluator, and a belief store, gated behind `learning`, `learning.evaluate`, and `learning.consolidate`. Four organs the layer would need to act on its own (an inferrer, a metabolism, a voice, and generalized consolidation) are not built, and three evaluation rules are measured but disarmed by contract, never moving a confidence. `open-brain learn mirror` names all of this itself, every time it runs.
- A folder named in a route's `read_order` is now served by that folder's `_index.md` before any file inside it, including files the same route names one by one. The index is the only document that can say which of its neighbours answers the question; ranking it under them spent the reading budget on whichever file happened to match a word.
- `open-brain health` now audits the reading path, not just index integrity: folders holding documents with no `_index.md`, index links that resolve to no file and no folder, indexed folders their parent index never mentions, and vault layers no route can reach. A well-formed catalog says nothing about whether a reader can arrive anywhere, and both failures survive every check that came before. They are reported as warnings, never as a broken vault, and `status` does not run the audit, so session start costs exactly what it did.
- `sync pending` and `sync show` now report how old a batch is: `prepared_at`, `age_days`, `stale` past two days, and a `stale_warning` telling whoever presents it to read `10_memory/_state.md` in full and confront every item with the real state first. `pending` also counts the stale batches. The stamp sits outside the content signature, so a batch identifier never changes and a batch written before the stamp existed still verifies; a batch with no readable stamp is treated as stale, because an unknown age is not a young one. The gate measures the age and stops there: whether an item is still true is semantic, and it stays the model's job.
- The living state now declares a budget per line as well as a ceiling for the whole file (`line_budget_day`, `line_budget_d1_d3`, `line_budget_d4_d7`, `line_budget_project`, `line_budget_closed`), and the stop hook checks it. Consolidation evicts whole sections, so a single line that swallows an entire day can sit just under the ceiling and leave the document unable to converge. Over budget, the turn ends with a soft block naming each line, its size, its budget and what to cut. New vaults are created with the keys in their front matter; generated blocks and sections with no budget are never judged.
- `PARITY.md`: a frozen, dated reference to the private engine this project owes a capability debt to, so a comparison against it stays a finite, answerable question instead of a moving target.
- Per-host integration references documenting exactly what gets written to `.claude/settings.json` and `.codex/hooks.json`, the merge rules that protect entries OpenBrain does not own, and where Claude Code and Codex differ.

### Changed

- `prefs add` now requires `--quote` and accepts `--domains`, `--why`, `--apply`, and `--source`. `staging add` has always demanded a citation, and every batch reaching the kernel through `sync validate` carries the proofs its candidates were staged with; the direct door was the only one that accepted a preference governing every turn with nothing behind it. Scripts that call `prefs add` need the flag added.
- The session-start injection no longer throws a line away whole for being too long. A state file that packs a whole day onto one very long line made its section inject nothing at all, every session, replaced by a bare truncation notice. A line that does not fit is now cut to the room left, marked with an ellipsis, and followed by a notice naming the section and the file to open for the rest. Below 400 characters of remaining room the head teaches nothing and the line is dropped, which the existing truncation notice already reports.
- The parity reference moved from snapshot `2026-07-a` to `2026-07-b` (2026-07-27). What the recapture adds to the comparison: a folder entry in a reading route resolved through the folder's index, and a stated preference entering the kernel at the weight it was stated with, carrying the citation that justified it. One difference is recorded as deliberate rather than closed, in PARITY.md: an explicitly stated preference does not close a staged candidate for the same rule here, because the gate is where that decision belongs.
- The parity reference moved again, from snapshot `2026-07-b` to `2026-08-a` (2026-08-02). What the recapture adds to the comparison: the age of a staged batch stated at presentation time, a state injection that cuts a line instead of starving the section that holds it, and a living state held to the per-line budgets it declares for itself. All three are the same lesson, which the module notes now carry: a writing rule that lives only in a document's header is not enforced, and a guard that cannot verify a claim can still refuse to let it pass in silence.
- Every seal the project writes is now keyed with a vault secret stored outside the vault, at `~/.config/open-brain/vault-<id>.key` (mode `0600`, `<id>` derived from the real path of the vault, created on first use, never written into the vault and never logged). Until now the frozen decision of a review, the batch, the apply state, the undo record and its seal, and the provenance journal of the preference kernel were all sealed with a plain sha256 of the very document they sealed, computed with a function this package exports. Anybody able to write a file in the vault could therefore write the record that vouched for it: a `<batch>.decision.json` approving everything was four lines of node, and it turned the human gate off, because `sync validate` stops asking for a human as soon as a decision exists. The seals are now HMAC-SHA256, one domain tag per kind of record, and the decision seal is bound to the batch it was made about so it cannot be lifted from the batch next door. This is a format break, and deliberately not a compatibility shim: reading an unkeyed seal as valid would leave the hole open. A batch prepared before this change must be prepared again, and a preference kernel whose journal predates it reads as `unverifiable`, never as `match`, until its next recorded write. See SECURITY.md for what moving or losing a key means.
- `sync validate` no longer treats the presence of `<batch>.decision.json` as proof that a human once decided. The waiver now rests on the file carrying the vault seal, which only a prior authenticated run could have produced; a decision file that is merely present is refused, and the run asks for a human as it would with no file at all. `sync undo` gets the same treatment: the waiver that lets an interrupted reversal finish without asking again used to rest on a `<batch>.undoing.json` anybody could write, and now rests on a token that record carries and only a run holding the vault key can produce. The `.undone.json` marker is sealed too, so a batch cannot be made permanently irreversible by dropping a file next to it.
- `sync undo` now validates every path in an undo record before it opens anything. A snapshot path travelled from the record straight into `join(root, path)` and then into a write or a delete, so an absolute path, or one carrying `..`, reached any file the user could write anywhere on the machine. Each kind of target is now held to its one legitimate location: the ledger and the rendered core to their exact paths, a loader mirror to the known loader filenames, a memory note to the same rule a note goes through when the gate writes one, symlink walk included.
- The tamper report for the preference kernel no longer prefers the fast comparison record over the evidence. It read `state ?? journal`, so a state file rewritten to describe an older write was believed without ever being held against the journal, and rolling both back to an older recorded state produced a clean `match`. The two are now always compared, any disagreement is reported as `unverifiable`, and the journal is chained, each entry carrying the seal of the one before it, so entries cannot be quietly removed from the end of it either.
- A weight bump approved through the gate is re-checked against the ledger inside the preference lock, at the moment of the write, rather than only during the preflight that runs before the decision is even frozen. A `prefs log` from another terminal in between was enough for a bump computed from 3 to land on a preference already weighing 4 and leave it at 5, while reporting the move the human had approved.
- The guard's protected perimeter is now the union of the configured memory path and the kernel's own hardcoded paths, imported directly from the redline module instead of re-derived. Renaming `memory:` in `vault.config.yml` used to be enough to walk the real kernel out of the guard's territory while `doctor` kept checking the original path; now the guard cannot lose track of the file the redline actually watches. `.open-brain/local/prefs-redline.json` (and its journal), every batch under `10_memory/staging/batches/`, and `vault.config.yml` itself are hardcoded into the protected set, not read from configuration: the files that carry a decision, a seal, or the perimeter's own definition were themselves unprotected before this, which is how a decision file or an undo waiver could be forged in the first place.
- The guard recognizes more of the ways a shell writes a file: `os.system`, `os.popen`, `subprocess.run`/`call`/`Popen`, and `child_process.execSync`/`exec` are now walked the same way `awk`'s `system()` already was, and an argument that is not a plain string literal is refused outright rather than let through unexamined. `gsed`, `vim`, `vi`, `nvim`, and `emacs` join `sed` and `ex` as recognized writers; `fish` joins the recognized shells; `xargs < file` is now read the same way as `xargs -a file` or a piped list, instead of only the latter two.
- `capabilities disable` and `hooks uninstall` now ask for the same proof of human presence as `prefs add`, because disarming a safeguard is a security decision and used to be reachable in one unattended command with nothing behind it. `prefs regen` rewrites the kernel's rendered core and loader mirrors from the ledger, and now asks for that same proof before it does, even though it can only ever restate what the ledger already holds.
- `staging compact` validates the month it derives from a candidate's `resolved_ts` before using it to build an archive path. An unvalidated value let a forged timestamp write outside the archive directory; it is now checked against `YYYY-MM` and refused otherwise.
- The human-presence check and the pre-effect guard are now named for what they are in README and SECURITY.md, not oversold: a terminal on standard input is an ergonomic signal a deliberately built automated caller can fake by opening its own pseudo-terminal, not a proof a human was present; the guard recognizes known ways of writing a file, widened every time a gap is demonstrated, and is not and cannot be a proof that no way remains. Both were already partially disclosed; both now say plainly what they do and do not catch, in one place (SECURITY.md's Known limitations) that README points to.
- README now lists the full command surface in one table, grouped by area, instead of leaving about half of it reachable only through `--help`.
- README states plainly that the package installs and runs as the `open-brain` binary.
- PRIVACY.md expanded substantially: what session-transcript reading covers, where, under what consent, exactly what redaction does and does not catch, how to turn it off, and how to erase everything derived from it.

## 0.1.0-alpha.2 - 2026-07-10

### Fixed

- Stale shard artifacts are removed when a vault shrinks below the shard threshold, so scans self-heal instead of serving records for deleted files.
- A corrupt or unreadable `vault.config.yml` is surfaced as a CLI warning and a health error instead of silently falling back to defaults.
- Expected CLI errors print a single clean line to stderr without stack frames or a duplicated message.
- Quickstart commands are pinned to the same version so the second command no longer resolves a different published spec.

## 0.1.0-alpha.1 - 2026-07-10

### Added

- Initial public release documentation and release controls.
- Real garbage collection apply mode with archive moves and re-checked guards.
- `route --suggest` command.
- Freshness change detection.
- `prefs add` command with automatic preference core regeneration.
- Free Mode `dismiss`, `check`, and `reset` commands.
- Layered onboarding flow.
- Packaging metadata for npm publishing.

### Fixed

- Delta note rotation.
